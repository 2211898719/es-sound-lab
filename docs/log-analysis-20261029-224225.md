## 根因与证据边界

### 日志请求频繁

0.2.1 中 `LogReader` 把 stdout/stderr 合并，并对任意一行进行 `contains("Permission denied")` / `contains("not permitted")` 检查，命中即主动抛出上述固定异常。这是确定的逻辑缺陷：扩展检测读取的其他应用权限拒绝日志，也会被误判为本应用日志通道失权。

原先命中的行在写入诊断前就抛异常，因此本文件没有触发原文和分离 stderr；无法断言这三次每一次都来自其他应用，也不能据此确认系统真实撤销读取权限。新版应避免猜测，记录原始 stderr 和退出码。

此外，扩展模式切换、规则改变会销毁仍有效的日志连接；异常每 5 秒重试使新授权请求持续出现。0.2.2 分别修复：stdout 只当数据、stderr 独立采集；复用连接；真正断流时暂停自动重试，只允许用户在前台主动重新连接。没有实现系统永久授权或 Shizuku 后端。

### 门/挡位音效无端被打断

0.2.1 中有多个未必发出新音效的全局停止路径：

- `resetSource()` 清空所有门/锁/挡位基线并 `audio.stop()`，即使重置的是不相关 Android / Mega 来源；
- 挡位无效、恢复或来源切换时 `audio.stop()`；
- `gearChanged()` 在检查组开关前先释放当前短音播放器；
- 大多数设置变化通过 `audio.refresh()` 全部停音。

这些代码足以解释没有实际新音效时的截断，但日志未记录每次播放器释放，不能把用户听到的每一次中断逐一归因。0.2.2 改为来源/播放组局部处理，关闭、静音、缺文件音源不会先抢占正在播放的短音。保持退出倒挡时立即停止倒车循环，不让门提示的完整性影响驾驶相关循环状态。

新可播放的高优先级事件、显式试听、手动停止、所播组被主动关闭或其输出改变、真实外部音频焦点丢失仍可中断。音源预检不能提前保证后续媒体解码或厂商路由成功，不能承诺所有播放失败都绝不影响前一个音效。

### 锁车音效

这次不是未校准，而是只有一个锁首样本、之后读取异常/重连，未建立可触发的连续变化。另一个软件问题是其他车辆来源重置也会清掉日志锁基线，导致后续锁值不断被当成首样本；0.2.2 按来源局部遗忘，模式/规则变化不重置仍有效的日志基线。

不能为“让它响”而直接把首样本当事件，否则重启、授权后读到当前状态就可能误播。校准 `1=闭锁、0=解锁` 仍需实车操作对照，本日志无法确认方向是否正确。不得静默反转用户配置。
