# 普通应用车辆事件接口：第一轮排查

日期：2026-10-30。目标是寻找厂商有意向第三方提供的只读状态或事件接口，不是获得厂商签名、修改权限或利用导出组件代读受保护属性。本轮只分析本地材料，没有连接车机、发送广播、启动/绑定厂商组件或调用Provider。

> 2026-10-31后续：用户已提供0.3.5提取的四包并通过完整性核验，逐包结论及新定位的讯飞平台服务线索见[四包实码复核](open-event-interface-investigation-20261031.md)。本文保留第一轮时点，候选宿主不等于已确认开放接口。

## 结论边界

- 23:33诊断已证明：本批固件、shell UID2000通过Mega属性管理器读取门、挡位、中控锁、AutoHold均被明确拒绝。该结果不能推导为所有厂商组件或全部第三方事件接口都不可用。
- 可以继续调查独立的状态广播、只读Provider、合作SDK/回调服务，但当前没有确认任何一条允许本应用取得上述四类事件的接口。
- exported=true、Manifest未声明权限、名字含query或callback都不是可用性证明。必须确认实际调用者检查、输入输出方向、返回语义、是否有副作用和运行时访问结果；没有文档或调用方证据的内部接口不称为官方开放API。
- 某组件能读车辆属性，不等于其他应用可以借它的身份读取。明确的访问拒绝按拒绝处理，不通过伪造包名/UID、修改白名单或调试入口解决。

### 广播方向核查

- 本批车辆服务DEX中未发现直接调用Android `sendBroadcast`、`sendStickyBroadcast`或`sendOrderedBroadcast`的指令。不能由此断言没有其他进程、依赖库或底层服务对外发布事件。
- 本批SystemUI五个DEX中找到58处直接广播发送调用点及17处`ContextCompat`封装调用点；这些数字是静态调用点，不是58/17种事件。可见候选主要涉及界面、对话框、应用入口、语音和手机无线充电UI，尚未确认向普通第三方广播门、挡位、中控锁或AutoHold的发送链路。
- 该扫描不是完整调用图或运行时跟踪，动态构造action、反射、其他封装和其他APK仍可能遗漏。不能把“当前未找到”写成“所有开放广播已排除”。
- 智行生活在包解析中声明接收`settemperature`、`testasr`、`queryLySeatInfo`等action，只说明它有对应接收路由；尤其不能将含query的action直接当作安全查询或擅自发送测试。

## 验证顺序

1. 从发送方与已知接收方共同确认协议，列明action/authority/组件、参数类型、接收权限、回调注册与取消、事件来源和初值语义。
2. 将接口分类：有明确第三方约定、已导出但仅内部使用、需签名权限、控制/调试入口。只有第一类且已核实无车辆写入副作用的接口进入只读候选。
3. 真要验证普通App开放性时，以本App原UID为准。shell调用成功不代表普通App能调用；保持包可见性、绑定、鉴权、有效样本和订阅分别记录。
4. 已确认的状态广播只被动监听；不发广播刺激车辆或模仿原厂客户端。未知Provider.call、服务启动或订阅动作先查实现，不能仅因名字像get/query就执行。
5. 只在停车P挡观察允许的车门操作，不为测试切挡或行驶。首样本只建基线，检查来源、类型、区域、有效状态与时间顺序；先记录、不播放音效。
6. 没收到事件不能直接判定不存在；结合发送端行为、触发条件、目标包限制和采集时长。明确权限拒绝不重试、不改身份。

第一轮静态排查本身未修改运行代码；后续0.3.5仅新增候选材料采集选项。结论仍是“存在值得继续核查的宿主，但尚无已确认的四类开放事件接口”，不是恢复原生音效成功，也不是证明只能使用日志。
