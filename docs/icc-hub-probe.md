# ICC 服务定位（0.3.22引入，0.3.23补全错误诊断）

## 实车操作

1. 使用原签名覆盖安装 `dist/es-sound-lab-0.3.23-debug.apk`，不要卸载旧版。
2. 若正在使用ICC来源监听，先手动点击“停止监听”。不会自动停止正式来源，也不会替用户改变来源、校准或音效设置。
3. 打开“车辆检测 → 更多 → ICC 服务定位（只读）”。打开页面不会联网；点击“开始单次定位”后只执行一次逻辑查询，最多5秒。开始按钮随后禁用；若确需重测，关闭弹窗后重新打开并手动开始。
4. 无需挂挡、开门、ADB、root、读取日志授权或更改工程模式。成功、失败或未列出均点击“导出记录”，提供 `ES-检测-时间.json`。
5. 检测结束后，如需继续原有ICC触发，手动恢复“开始监听”。本次定位不自动恢复监听。

## 固定只读范围

- 仅通过显式HTTP代理 `192.168.55.31:51020` 请求 `GET http://ota_proxy/info`，无请求体，不解析逻辑域名的DNS。
- GET带随机Seed以适配原厂响应信封；按响应自身Seed解密，不要求与请求Seed相同。原厂空InfoRsp可能没有Content-Type，保留为空结果，不伪造路由。
- 连接/读取超时各1500ms，传输总期限3500ms，整体检测5000ms；请求串行、单次、无应用级自动重试。拒绝重定向、压缩响应、超32KiB响应及无效protobuf。
- 最多处理128条路由，仅保存 `ota_icc_vsi` 和 `ota_android_vsi` 的模块名、地址及存在时的端口；其余模块与trace不导出。未知地址格式只保留脱敏状态，不输出原文。
- 不访问返回地址、不扫描端口、不调用 `/register`、控制、事件、复位、升级或信息/VIN路径；不启动、停止或重配原厂服务。
- 与ICC正式监听及独立限时车况检测互斥。定位期间显式启动ICC车况会取消定位；关闭弹窗、导出、进入后台、服务销毁均停止未完成定位，丢弃迟到回复。正式ICC监听原有生命周期不变。

## 导出与解释

普通检测JSON新增独立对象 `iccHubProbe`，不与 `iccVehicleProbe`、`iccVehicleSource` 混用。它包含sessionId、检测时间、固定代理/逻辑目标/路径/方法、只读标记、次数/期限、结果阶段、HTTP状态（取得时）、耗时以及筛选后的routes。结果跨进程持久化；历史进行中标记为中断，不自动重试。清空记录会清除持久化定位结果。

| 结果 | 含义 |
| --- | --- |
| complete | 读取到ICC路由登记，不能单凭地址确认提供者进程或云端依赖 |
| target-not-listed | 本次回复未列出ICC，包括空响应；不能推断服务不存在 |
| http-NNN / failed / invalid-response / timeout | 拒绝、通信、结构或超时失败，不切换其他入口；仍可导出 |
| stopped / previous-session-interrupted | 主动停止或历史中断；不会恢复请求 |

`addressKind`仅给出有限提示：

- `head-unit-address`：匹配已核验的192.168.55.31或明确回环地址。不能据此把端口归属到具体包。
- `other-address-unconfirmed`：其他符合地址字符格式的地址，可能是另一节点或其他地址；不直接判定云端、QNX或Android。
- `local-module-or-unspecified`：地址为空，兼容原厂本地模块登记，但不能排除地址未指定。
- `unrecognized-address-redacted`：地址格式未识别，原文未导出。

返回多条ICC登记时全部保留，不随意选择一条为“唯一提供者”。本机代理已确认，不代表完整链路已证实无云端依赖。拿到实车路由后再针对对应节点或进程分析，不要求先批量提取更多APK。

## 0.3.23失败信息

用户反馈0.3.22点检测后显示IOException，尚未提供这次导出，因此不能确定是连接、HTTP帧、响应体、信封还是解密失败。旧版对未知异常仅保留类名，且异常发生在响应体读取时会丢掉已获得的HTTP状态。本版修复的是这一诊断缺口，不声称已经修复尚未定位的实车通信故障。

失败时`iccHubProbe.failure`保存固定阶段`stage`、安全类别`reason`、标准异常类型`errorType`；传输层还按实际取得情况保存HTTP状态、响应类型分类、编码分类、声明/收到字节数、响应Seed是否存在（仅布尔值）、耗时及是否到达总期限。不保存原始异常消息、堆栈、异常cause、Seed内容、密钥或原始响应；未知异常不会把任意小写短消息当作安全错误码。

| stage | 能说明什么 |
| --- | --- |
| open-proxy / configure-get | 创建连接对象或配置请求失败，不能推断已连到服务 |
| response-status | 连接或读取HTTP状态行失败；没有HTTP状态时明确标注尚未取得，不伪造状态 |
| response-headers | 已收到状态，检查响应头期间失败 |
| response-body | 已收到状态，但响应体读取失败；保留已接收/声明字节数 |
| response-envelope / decrypt-response | 响应信封不符合预期或解密失败，不保存响应明文 |
| decode-routes | 已取得回复，但路由结构解析失败；保留有限解析错误码，不猜路由 |

`unexpected-eof`仅说明流提前结束，不据此认定接口不存在；`connection-reset`为连接重置；无具体errno的ConnectException仅记为`connection-failed`，不会一律推断拒绝连接。未确认原因的IOException记为`io-error`并显示阶段。总期限导致的断开归为`timeout`，无效状态码-1归为协议异常，不导出HTTP -1。原固定GET、响应大小上限、互斥、取消与失败不自动重试规则均不变。

重测一次后，无论哪种失败均导出普通`ES-检测-时间.json`；不是必须另跑ADB诊断，也不要求挂挡或提取更多APK。
