# ICC正式车况来源（0.3.21）

本文保留0.3.21历史设计。当前0.3.30的来源分工、默认监听、车速映射与持续自动重试以`docs/interface-and-authorized-log.md`及`docs/icc-reconnect-and-lock-focus-20261101.md`为准；下文“失败即停、手动重连”仅描述旧版。

## 实车证据与边界

用户提供`ES-检测-20261101-015410.json`（App 0.3.19）。ICC会话在2026-11-01 01:53:18至01:54:02（UTC+8）取得30次HTTP 200和30个有效挡位，44.387秒内P→D→P→D→P，共4次变化，证明此车上该固定查询路径能返回变化的P/D快照，而非只有连接成功。

查询耗时6–1410ms，中位数14.5ms，部分约1208ms；旧版回复间隔1007–2411ms，包含每次完成后约1000ms等待。没有车辆动作源时间，不能测定真实端到端延迟，也不能由此保证其他字段或车型可用。`handbrakeRaw`在1/2间变化，不等同AutoHold；power=3、charging=1、lock=1保持不变，车速字段没有出现。不得把缺失车速当0。

用户随后明确确认挡位成功。本版新增五项状态及锁/充电触发尚待实车核验；后台长时间稳定性、R/N挡仍需单独验证。R/N映射仅来自已检查的原厂protobuf定义；M没有对应枚举，不合成。

## 启用与轮询

覆盖安装0.3.21后，在“车辆检测 → 来源 → ICC车况”选择间隔并确认。升级保留原来源，不擅自切换或开启音效。未开始车辆监听时只保存选择，不发请求；已监听时显式确认会切换来源，停止旧文件/logcat读取及独立车辆探针。

- 默认完成后等待250ms；可选500ms或1000ms。三个预设均有下限，不允许0或无限并发；非法设置退回250ms。
- 实际轮询间隔是**请求耗时+配置等待+调度开销**，不是固定4Hz，也不是车辆源信号刷新率。已有约1.2秒的请求不能通过缩短客户端等待消除；短暂的中间挡位仍可能漏采。
- 单后台工作线程，当前请求完成并在主线程处理后才排下一次，没有追赶积压或重叠请求。
- 沿用固定代理、`ota_icc_vsi/cdt`、固定EmptyReq和响应解密/白名单；不新增路径、权限、扫描、鉴权变更或控制调用。
- 沿用连接/读取1500ms、定时断开3500ms、响应32768字节上限。网络/HTTP/解密/结构错误即停，不重试、不回退日志；面板显示错误，需手动“重新连接”。

监听期间持续查询，不受独立检测30次/60秒限制；前台服务按现有车辆监听策略运行，退出检测页或App进入后台不会主动停止。停止车辆监听、服务销毁、切换来源或改间隔会关闭旧连接、取消定时任务、丢弃晚到结果。用户已经保存监听开启时，沿用现有服务/开机恢复策略；恢复始终新建静默基线，持久化历史不作为新信号。

“更多 → ICC只读车况检测”仍是独立的限时工具，保留1秒/30次/60秒和不播音规则。正式ICC监听期间不允许再启动独立ICC探针，避免双重请求。关闭探针弹窗或导出不会误停正式来源。

## 事件与时效

同一查询的六个白名单字段接入状态大屏；不增加查询次数。挡位沿用现有TransitionGate、音效开关、用户音源/音量。ICC原始枚举为1=P、2=N、3=D、4=R，分别转换为本App的P=1、N=3、D=4、R=2，不能套用ES日志数字预设。当前P/D已实车观测，R/N协议定义待实测。

| 字段 | ICC协议值 | 展示/触发边界 |
| --- | --- | --- |
| 手刹/EPB | 1释放、2拉起 | 只展示，不是AutoHold，无相关音效 |
| 电源 | 1 OFF、2 ACC、3 ON、4 START | 只展示，不推断车辆可行驶 |
| 充电 | 1未充电、2待机、3慢充、4快充 | 默认只展示，单独确认后且音效组开启才允许开始/结束事件 |
| 中控锁 | 1解锁、2闭锁 | 未核对前显示协议候选；独立ICC确认、音效组和已确认车外输出均满足才触发 |
| 车速 | 原始整数 | 单位未确认，不标km/h、不换算、不驱动持续循环音；缺失不当0 |

锁和充电分别点击卡片核对，并勾选本来源触发确认。偏好icc.lock.confirmed、icc.charge.confirmed默认false；不继承旧日志锁校准或ES预设，不自动开启音效组/车外输出。充电将1/2归为非充电、3/4归为充电，仅两类之间变化播报，慢快切换和未充电/待机切换不重复。此为协议快照状态，不等同插拔枪或完整充电会话保证。保存/撤销确认丢弃已在途旧查询并重新建立静默基线；撤销、未知或失效取消对应音效。

首样本不播，重复值不播；未知/缺失清除基线，恢复首样本不播。校准模式不播，进入/退出或保存校准会丢弃此前发起的查询，结束后重新静默建基线。ICC固定协议不允许通过日志映射改写，校准卡片显示协议解释。

请求至主线程处理超过5秒的结果丢弃；超过5秒无新快照清除全部ICC基线、实时卡片及待播音效，含只读车速。停止/错误/切换来源同样清除。每个字段独立处理缺失/未知，不以挡位是否有效决定其他字段可用性，也不把缺失默认为0/关闭/释放。已有回复是查询快照，没有验证车辆源时间，显示“最近回复/不保证当前”，不能靠这些检查证明上游永不缓存。

没有扩展六字段白名单，不接入车门/尾门/车窗/电池/AutoHold，不触发日志旧自定义规则。倒车、行人、声浪持续循环不自动启用；用户手动试听保留既有输出保护。

## 记录与验收

导出`iccVehicleSource`与独立`iccVehicleProbe`分开；`eventBackend=icc`沿用既有偏好键`log.backend`，不迁移旧用户设置。记录配置间隔、请求/200/有效挡位/变化次数、最近耗时、错误或基线阶段、丢弃数，以及最近最多30个白名单快照；计数可持续增长，历史有界。新增`iccConfiguration`记录间隔、锁/充电确认，以及speedUnitConfirmed=false、handbrakeIsAutoHold=false。原始二进制、真实Seed、密钥和网络错误正文不记录。

报告约每5秒保存一次，启动/停止状态变化立即保存，避免每250ms写偏好；进程重新加载的活动报告标记中断，不恢复为实时状态。清空检测记录会清除已保存报告，若正式监听仍在运行，后续新回复会重新生成记录。

安全驻车对照：

1. 保留原签名覆盖安装、不卸载；选择ICC来源并确认250ms，启用需要的挡位音效。
2. 开始监听。初始P应只显示、不播音；在车辆允许且持续制动条件下对照P/D变化与音效，不需行驶。
3. 检查大屏来源ICC、原始1/3与P/D显示；不要用其他状态“未收到”推断其关闭。
4. 如需R/N验证，在安全条件下单独对照；停止/重连/校准结束后的首样本不应补播。
5. 保留后台运行一段时间，失败、变化0或正常均导出JSON，检查新`iccVehicleSource`，而非只看旧限时探针报告。

6. 新五项先仅看显示：安全驻车核对手刹、合适条件下的充电/锁及电源。车速只读原值，不为验证速度要求行驶。缺失不代表车辆状态为0。确认充电/锁枚举与真实动作一致后再分别允许触发；锁仍需亲自验证车外输出。AutoHold、门、尾门不会因本版自动可用。

本地测试使用注入传输、模拟音频和本机回环代理，不连接真实车机；截图注明模拟，不能当成新版本实车音效验收。最终构建与签名记录见项目交接文档。
