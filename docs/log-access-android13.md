# Android 13 日志授权与替代读取方案

核对日期：2026-10-29。适用背景：实车为 Android 13，用户截图显示“允许 ES 音效实验室访问所有设备日志吗”，按钮为“允许一次 / 不允许”。下文把标准 Android 机制、项目行为和待验证方案分开；厂商固件可能不同。

2026-10-30补充：用户已通过MegaEngineeringMode开启ADB并提取车机APK，ADB可用性得到用户确认；root、Shizuku、shell车辆权限及重启后恢复仍未知。新样本的直接车辆订阅与车外音频发现见[APK接口分析](vehicle-apk-research-20261030.md)，当前App仍未接入shell桥。

## 1. 确认的系统机制

以固定版本 AOSP `android-13.0.0_r1` 为依据：

- `READ_LOGS` 资格与本次设备日志读取的用户确认是两层检查；已有权限不代表新读取请求已批准。
- `LogcatManagerService` 缓存批准/拒绝状态 60 秒。缓存过期后的新请求可能再次询问，不是每隔 60 秒强制终止已打开的日志流。
- 普通新请求只有 UID 处于 `PROCESS_STATE_TOP` 时才弹确认，否则拒绝；已有短期批准等分支另行处理。前台服务不等于前台 Activity。
- 测试 instrumentation 有专门路径，不作为生产免授权方案。
- logd 对 UID 小于应用 UID 起点的客户端免做该用户确认；这不是给普通 APK 设置一个标记就能取得的身份。

以上分别见来源 [1]—[3]。因此，重复 `pm grant` 不代替此次批准；再次出现弹窗不能单独证明权限被撤销或整机重启。普通 APK 也没有由这套实现提供的“永久允许”开关。

## 2. 项目请求行为与 0.2.2 修复

0.2.2 已完成连接复用：开始/结束扩展检测、修改规则只切换读线程过滤或重建车辆接口，保留同一 logcat 进程、日志 generation 和仍有效的锁/门基线。stdout 不再匹配权限拒绝文字，stderr 独立限量记录。真正输出结束或启动异常会记录退出码/异常，暂停自动重试，需要用户回前台点击“重新连接”。无权限时只轮询权限标记，不启动日志请求。

这减少应用自己触发的新请求，**不是永久授权**。实际断流期间不能自动恢复监听；如果车机仍然频繁结束流，先依据 stderr/退出码判断，不再靠无限重试掩盖原因。

下面保留 **0.2.1 旧版行为** 作为问题背景，不能按当前实现理解：

`LogReader.java` 使用 `ProcessBuilder` 在应用身份下启动 logcat，非 shell / Shizuku 身份。没有权限时等待；请求结束后约 5 秒重试。

`MonitorService.java` 的 `restartSources()` 同时重建车辆接口与日志读取，调用入口包括：

- 开启监听；
- 开始、结束扩展检测；
- 用户点击重新连接；
- 修改规则；
- 服务重建后恢复监听。

这是旧版代码可观察的行为，不证明每次调用都弹窗：是否出现窗口还与系统批准缓存、前后台状态和厂商实现有关。0.2.2 已实现连接复用，但仍未接入特权免弹窗后端。

## 3. 方案比较

| 方案 | 前提与作用 | 不能保证的部分 | 当前状态 |
| --- | --- | --- | --- |
| 复用同一日志连接 | 无新增特权；把车辆源重建与日志源重建分离，在应用内切换过滤，减少新请求 | 进程被杀、系统重启、日志服务断线后仍需新请求 | 0.2.2 已实现，待实车回归 |
| Shizuku UserService | 用户安装、启动并授权 Shizuku；由 shell/root 身份服务读日志，经 Binder 传回 | 厂商 SELinux/日志策略、后台清理仍需验证；非 root 启动在整机重启后需要重新执行 | 待确认车机条件，未接入 |
| ADB shell 日志桥 | 用户明确开启并授权调试；shell 进程采集，受控通道传给应用 | ADB 可用性、整机重启后的重启方式、鉴权和连接恢复 | 候选，不默认开启网络端口 |
| 已获授权的 root 服务 | 已有 root 且用户授权，可研究受控的启动/采集服务 | 不保证功放常电或跨深度休眠播音，不建议为本应用解锁/刷写车机 | 条件未知，未实现 |
| 厂商车辆接口 | 官方或系统授予读取所需权限，直接订阅锁/挡位等属性，减少对日志依赖 | 当前 Mega 读取已被拒绝；合法权限与可用 API 仍待确认 | 长期优先研究 |

Shizuku 官方 API 支持在独立 UserService 中执行 shell（UID 2000）或 root 身份代码；新接入应研究 UserService 而不是依赖旧 `newProcess` API。仅安装 Shizuku 不会改变本应用当前 `ProcessBuilder` 的身份。参见来源 [4]。

非 root Shizuku 的官方说明明确：整机重启后需要重新启动；Android 11+ 可通过设备内无线调试启动，但车机是否开放此功能尚未确认。因此不能把它宣传成无需任何启动条件的永久授权。参见来源 [4]、[5]。

## 4. 连接复用实现与限制

0.2.2 按以下方向实现并加入回归，仍需车机实测：

1. 分开车辆接口与日志连接的生命周期、generation token，不让车辆接口重建丢弃仍有效的日志回调。
2. 保持一个有界日志流，由应用内过滤切换标准/扩展模式；评估宽范围采集对主线程队列、CPU 与隐私的影响，不能简单永久保留所有日志。
3. 规则改变只更新匹配并重建必要车辆订阅；检测切换不关闭 logcat。真正断流暂停自动重试，由用户前台主动重连，避免重复系统窗口。
4. 过滤模式切换不能把旧日志当新锁车事件；来源恢复仍建立基线，不补播过期动作。
5. 回归覆盖开启/结束检测、规则改变、旧回调、真正断流、拒绝授权和服务重建，再检查实车窗口数量。

## 5. 如果接入 Shizuku / shell 后端

同样属于后续设计：

- 保留普通读取作为明确选择的后备；界面和导出显示实际后端、UID、连接与授权状态，不把 Shizuku 授权混同为 Android 日志窗口批准。
- 采集服务只接受预定义日志参数，不暴露任意 shell 执行或无鉴权的远程控制接口。
- 只传必要车辆日志，应用内继续执行解析、噪声过滤、时效检查、去重与基线保护；队列要有上限。
- 显式处理 Binder 死亡、用户撤销授权、后端未启动和设备重启。失败时不要每 5 秒反复唤起授权界面。
- 用户停止监听后释放采集资源。选择常驻/跨进程采集必须告知用户并提供关闭方式。
- 先验证车机可用性和最小读取，再接事件触发；锁音效的独立车外路由约束保持不变。

## 6. 不采用的做法

- 不自动点击“允许一次”，不以无障碍模拟点击冒充稳定授权；后台或休眠时弹窗本身也未必出现。
- 不推荐修改系统 logd、全局关闭确认或盲目调整隐藏配置；影响所有设备日志访问，风险与兼容性不可控。
- 不为免窗口将量产应用作为 instrumentation 常驻运行。
- 不把“前台服务 + 长期唤醒锁”当作永久日志授权或整车不断电方案。
- 不未经验证就宣称通过 `pm grant` 可解决 Mega 自定义权限或全部日志确认；这些路径有不同授权条件。

## 7. 实车验证清单

10月30日已确认ADB可用；仍缺少无线调试配对、Shizuku / root、shell直接车辆读取权限和重启恢复条件。下一轮先采集这些条件，避免将ADB连接成功当作全部车辆权限已获准。

测试时分清以下情况：

1. 只是界面重新打开、应用进程重启、监听服务重建、屏幕唤醒还是整机重启？对照 `runtime` / `sessionHistory` 的进程/服务 ID、启动计数和单调时钟，未知启动计数为 -1 时不据此判断。
2. `readLogsGranted` 是否改变？是否记录了新 logcat 请求？首条车辆日志有没有到达？
3. 新请求发出时 Activity 是否在前台？本次有没有用户批准？窗口出现不是车机重启的独立证据。
4. 切换检测、修改规则、手动重连与真正断流分别测试，不混成一次“重启”。
5. 即使读取恢复，仍要单独验证锁状态校准、自动播放请求、实际路由和物理车外功放。

建议先验证 0.2.2 连接复用并完成清醒状态的自动锁/解锁测试，仍无法保持读取时再研究显式授权的日志桥；没有 root/系统集成条件时，不承诺整机重启后的完全无人值守。
